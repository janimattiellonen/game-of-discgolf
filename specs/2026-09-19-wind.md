# Wind

**Status:** not implemented — design only
**Date:** 2026-09-19
**Prompt:** `prompts/wind.md`

## Problem Statement

Every throw in the game happens in dead air. The disc leaves the hand at an angle and a carry,
both drawn from the scatter curves, and nothing between the lie and the landing point has any
opinion about where it goes. The board has terrain — a water band, a raised plateau — but the
*air* over that terrain is inert.

Wind is the first force in this game that acts on the disc after release, and it is different
in kind from everything already modelled. Scatter is noise: it is symmetric, it has no
direction you can read, and the only defence is to throw softer. Wind is a **bias**: it is
visible before you commit, it is the same for everybody standing on that spot, and the defence
is to aim off. That is the whole reason to add it — it turns aiming from "point at the basket"
into a judgement, and it is the first mechanic where the right answer is *not* the line to the
pin.

This spec covers a wind **field** over the board, an indicator that reads it, and a deflection
model that bends a throw. It is deliberately the simple version: the disc still flies in a
straight line. There is no S-curve, no hyzer or anhyzer, no per-disc stability. Those are
named in **Out of Scope** and the model here is shaped so they can be added as more terms in
the same deflection function rather than as a rewrite.

Assume a right-hand backhand throw throughout, as the prompt does. Every "turns right" and
"fades left" below is written from that assumption, and the day a forehand exists, every sign
in this document is a flag.

## Units

Wind speed is a velocity, so it goes in the model as **tiles per second**, and it is authored
in **m/s**.

This is not a new rule, it is the existing one. `TILE_M = 5` metres per tile, and seconds are
seconds, so the metres-to-tiles conversion for a *speed* is the same `tl()` that converts a
*distance*:

```ts
tl(6)   // 6 m      -> 1.2 tiles
tl(6)   // 6 m/s    -> 1.2 tiles/s
```

The identity is worth stating out loud precisely because it looks like a coincidence. It is
not: `tl` divides by `TILE_M` and the time dimension passes through untouched.

**Display is km/h, plus the Beaufort band name.** km/h is the unit the prompt asks to read,
and Beaufort answers the question the prompt raised about upper limits — it is an open-ended
real scale that already names calm through hurricane, so authoring a storm later adds a row of
data and retunes nothing.

```ts
/** tiles/s -> km/h. TILE_M metres per tile, 3600 seconds per hour. */
export const kmh = (tilesPerSec: number) => tilesPerSec * TILE_M * 3.6;
```

One tile/s is 5 m/s is 18 km/h — a gentle breeze, Beaufort 3. That is the number to hold in
your head while reading the tuning below.

```ts
const BEAUFORT: { max: number; name: string }[] = [
  { max: 1, name: 'calm' },
  { max: 5, name: 'light air' },
  { max: 11, name: 'light breeze' },
  { max: 19, name: 'gentle breeze' },
  { max: 28, name: 'moderate breeze' },
  { max: 38, name: 'fresh breeze' },
  { max: 49, name: 'strong breeze' },
  { max: 61, name: 'near gale' },
  { max: 74, name: 'gale' },
  { max: 88, name: 'strong gale' },
  { max: 102, name: 'storm' },
  { max: 117, name: 'violent storm' },
  { max: Infinity, name: 'hurricane' },
];

export const beaufort = (kmhSpeed: number) => BEAUFORT.find((b) => kmhSpeed < b.max)!.name;
```

Shaped exactly like `CLASSES` and `classOf` in `scale.ts`, which does the same job for hole
length. Two lookup tables with the same shape is a pattern; two with different shapes is a
puzzle.

### The direction convention, stated loudly

**A wind's direction is the heading it blows TOWARD**, in radians, in the same tile-space
angle convention as a throw.

Meteorology names winds by where they come *from* — a northerly blows southward. That
convention is correct for forecasts and wrong for this codebase, because the value here is a
velocity vector that gets added to a disc, and a vector that points backwards from what it
does is a bug factory. The on-screen arrow points the way the wind pushes, which is also the
only thing a player needs.

The other sign that matters:

> **A positive angle offset is the thrower's right.**

Tile-space `y` grows southward and `proj()` in `render.ts` is orientation-preserving — its
matrix determinant is `TW * TH / 2 > 0` — so a clockwise rotation in the model stays clockwise
on the canvas. Heading `0` is east; heading `+90°` is south, which is on the right hand of
someone facing east. Every "turns right" in this spec means **add** to the angle.

## The Field

### One area

```ts
// src/game/wind.ts
export interface WindArea {
  /** centre of the area, in TILES */
  at: Vec;
  /** the heading it blows TOWARD, radians */
  dir: number;
  /** speed across the whole core, tiles/s */
  speed: number;
  /** full strength out to here, tiles */
  core: number;
  /** tapered away to nothing by here, tiles */
  radius: number;
}
```

An area has a **body** and an **edge**, and they are two separate numbers. Inside `core` the
wind is at full authored strength; from `core` to `radius` it thresholds away to nothing.

```ts
/**
 * Flat across the core, then a smooth threshold out to radius. Zero slope at BOTH ends, so
 * there is no rim to feel and no point-peak to hunt for.
 */
export const falloff = (d: number, core: number, radius: number) => {
  if (d <= core) return 1;
  if (d >= radius) return 0;
  const u = (d - core) / (radius - core);
  return 1 - 3 * u * u + 2 * u ** 3; // 1 - smoothstep(u)
};
```

The obvious single-radius kernels are both worse, for opposite reasons:

- **A Gaussian never reaches zero.** "Where does this area stop" has no answer, every area
  quietly touches every point on the board, and the ring drawn on the canvas is a polite
  fiction.
- **A single-radius taper — `1 - d/r`, or the bisquare `(1 - (d/r)²)²` — peaks at one point.**
  An area authored "6 m/s" then delivers 6 m/s at its epicentre and nowhere else; bisquare is
  already at half strength by 54% of the radius. That is a point source wearing the word
  *area*. The prompt asks for regions of wind, and a region has to have an inside.

Two properties earn the core-and-threshold shape its place:

- **The authored speed is the speed you actually feel**, everywhere in the core. `speed` means
  something a player can experience, which is what makes tuning it possible.
- **Its slope is zero at both ends.** At `core` and again at `radius`, because `-6u(1 - u)`
  vanishes at both. A disc crossing either boundary feels the wind come on and drop away
  gradually. A linear taper has a kink at each end, and a kink in a force field is something a
  player can feel without being able to name — the worst kind of artefact.

Because smoothstep is symmetric about its midpoint, **half strength sits exactly halfway
through the taper band**. An area authored `core: 20 m, radius: 45 m` is at full strength to
20 m, half strength at 32.5 m, and gone by 45 m — authoring by arithmetic rather than by
guesswork, which the bisquare's 0.54 never allowed.

`radius` is still a hard outer bound and that part is worth keeping. It is what lets `windAt`
skip an area in one comparison, and it is what makes the outer ring on the canvas a true
statement rather than an approximate one. The softness the prompt asked for lives in the band,
not at the boundary.

### Many areas

```ts
export const windAt = (f: WindField, p: Vec, t: number): Vec =>
  f.reduce((w, a) => {
    const k = falloff(dist(p, a.at), a.core, a.radius);
    if (k === 0) return w;
    const { dir, speed } = gust(a, t);
    return { x: w.x + Math.cos(dir) * speed * k, y: w.y + Math.sin(dir) * speed * k };
  }, { x: 0, y: 0 });
```

**Vectors sum, speeds do not.** Two areas blowing against each other cancel where they
overlap, leaving a calm seam between them; two blowing the same way reinforce. Both are the
right answer and both fall out of the addition, which is the argument for storing a field of
vectors rather than a field of speeds.

It has one consequence that looks like a bug and is not: **the resultant in an overlap can
exceed every individual area's speed.** Two 6 m/s areas whose cores overlap and whose headings
agree give a flat 12 m/s across the intersection. There is no clamp, deliberately — clamping
would put a dead spot in the middle of the most interesting part of the board. A test asserts
it, so that nobody arrives later, reads the authored table, sees 12 m/s on screen and "fixes"
it.

It is also the authoring rule the core gives you for free: **overlap the tapers freely, and
overlap two cores only when a genuinely wild pocket is the intent.** Cores are where the
speeds add at full value; the bands are where they blend.

Heading matters as much as strength, and on this hole it matters more. The two areas below are
90° apart, so where they meet the resultant barely grows — it *rotates*. Walking up the
fairway, the wind swings from cross to head rather than getting stronger, which is the more
interesting of the two things a second area can do.

With no areas in range, `windAt` returns the zero vector and every downstream term is exactly
zero. Calm is not a special case in the code; it is the ordinary case with nothing in it.

### Fluctuation

The prompt asks for wind that "is not static and may fluctuate a bit," with speed that
fluctuates "but normally not so much." That is a small, smooth, continuous wander — not
jitter.

```ts
export const GUST_DIR = rad(12);  // peak wander either side of the base heading
export const GUST_SPD = 0.18;     // peak fractional wander in speed
const P1 = 3.1;
const P2 = 7.3;                   // seconds; incommensurate, so the pattern does not visibly loop

/** Two sines with unrelated periods. Range [-1, 1], smooth, and a pure function of t. */
const wobble = (t: number, phase: number) =>
  0.6 * Math.sin(t / P1 + phase) + 0.4 * Math.sin(t / P2 + phase * 2.3);

export const gust = (a: LiveArea, t: number) => ({
  dir: a.dir + GUST_DIR * wobble(t, a.phase),
  speed: a.speed * (1 + GUST_SPD * wobble(t, a.phase + 1.9)),
});
```

Direction and speed read `wobble` at different phases, so they do not peak together — the
gusts back and veer instead of merely pulsing.

**This is a function of time, not a call to `Math.random()`.** Sampling a random number per
frame would produce a direction that jitters at 60Hz, which reads as a broken arrow rather
than as weather, and it would be untestable. It is the same rule the flier follows in the disc
types spec: randomness enters at the edge, as a parameter, and the physics stays pure.
`wobble` can be asserted for smoothness, for bounds, and for not repeating inside a round.

`P1`, `P2`, `GUST_DIR` and `GUST_SPD` live in `wind.ts` beside `wobble` rather than in
`constants.ts`. They are not independent tuning scalars — they are the four parameters of one
curve, and split from the function they parameterise they mean nothing. The **coupling**
constants in the next section do go in `constants.ts`, because those are exactly like
`SKID_DECEL`: one number, one physical effect, tunable alone.

### The per-round roll

Areas are authored as hole data. What a player actually faces is an area plus a **roll**,
drawn once when the round starts:

```ts
export interface WindRoll {
  /** radians, added to the area's base heading */
  dir: number;
  /** multiplies the area's base speed */
  gain: number;
  /** gust phase, so two areas do not gust in lockstep */
  phase: number;
}

export const ROLL_DIR = rad(25);
export const ROLL_GAIN = [0.7, 1.3] as const;

/** Three rolls in [0, 1). The caller draws them; this stays pure. */
export const rollArea = (a: WindArea, r1: number, r2: number, r3: number): LiveArea => ({
  ...a,
  dir: a.dir + ROLL_DIR * (r1 * 2 - 1),
  speed: a.speed * lerp(ROLL_GAIN, r2),
  phase: r3 * Math.PI * 2,
});
```

Without this, the wind on this hole is a constant, and a constant force on a fixed board is
indistinguishable from having re-tuned the board — you would tune around it within three
throws and never learn anything about wind. The roll is also what makes `reset()` worth
pressing.

`createState()` draws `3 × WIND_AREAS.length` numbers and stores the resulting `WindField` on
`GameState`. **`reset()` re-rolls**, which puts it with `lie` and `throws` — the things a new
round replaces — rather than with `mode` and `toggles`, which are preferences it preserves.
New round, new weather.

The field is otherwise immutable for the whole round. A `LiveArea` is only ever read.

### This hole's areas

```ts
// src/game/course.ts, beside TEE, BASKET and isWater
export const WIND_AREAS: WindArea[] = [
  // Over the water, perpendicular to the tee-to-basket line and pushing toward the bridge
  // side. The wind itself nudges the greedy carry toward safety - it is the COMPENSATION
  // that is dangerous, because aiming off into it means aiming deeper over the hazard.
  { at: { x: 8, y: 6.5 }, dir: rad(57), speed: tl(6), core: tl(20), radius: tl(45) },
  // On the plateau, blowing back down the fairway. Approaches into the pin are into the
  // wind, so they turn right, off the high ground and toward the short side.
  { at: { x: 16.5, y: 2.5 }, dir: rad(147), speed: tl(5), core: tl(15), radius: tl(30) },
];
```

Their cores are 35 m of combined radius across 47 m of separation, so they are disjoint: there
is no double-strength pocket on this hole, only the rotating band between them.

Two areas, not three. The board is 100 m × 70 m and these two tapers already overlap across
the middle of it; a third at this scale would have nowhere to be that is not inside one of
these. Three is what the field code supports and what a larger hole will want — see
`specs/2026-09-19-course-measurement-and-hole-classification.md`, where per-hole geometry is
the blocking item — and `WIND_AREAS` is an array precisely so that adding one is data.

Both headings are authored relative to the tee-to-basket line, which runs at −33°. Area 1 is
perpendicular to it (−33 + 90), area 2 is antiparallel (−33 + 180). That is not a coincidence
to be preserved by future tuning; it is how these two were chosen to do one specific job each
on this one hole, and per-hole geometry will re-author them anyway.

## Deflection

### Where it goes in the pipeline

Wind is applied in `release()`, **after scatter, before the flight starts**:

```
throwDist(p)  ->  d0
scatter       ->  a, d          (unchanged)
wind          ->  a', d'        (new)
startFlight(s, lie, a', d', false)
```

Scatter is the throw you made; wind is what the air did to it. They compose in that order and
`Flight` never learns that wind exists — `from`, `to`, `a` and `d` mean exactly what they mean
today, so `basketEvent`, `skidPath`, `drawDisc` and `land()` are untouched.

Critically, **wind does not feed back into scatter**. `sigA` and `sigD` are evaluated from the
intended carry, and stay that way. This is the same invariant the disc types spec pins for the
flier: the spread of a throw is a property of how hard you threw it, never of how it turned
out. Ordering them the other way would make a tailwind widen your cone, which is both wrong
and invisible.

### The model

```ts
// physics.ts
export function windDeflect(lie: Vec, a: number, d: number, f: WindField, t: number) {
  const dir = { x: Math.cos(a), y: Math.sin(a) };
  const end = { x: lie.x + dir.x * d, y: lie.y + dir.y * d };

  // Average the field along the NOMINAL line. Sampling one point would make a field of
  // areas pointless: a throw that crosses a gust pocket has to feel the pocket.
  let w = { x: 0, y: 0 };
  for (let i = 0; i < WIND_SAMPLES; i++) {
    const u = i / (WIND_SAMPLES - 1);
    const s = windAt(f, { x: lie.x + (end.x - lie.x) * u, y: lie.y + (end.y - lie.y) * u }, t);
    w = { x: w.x + s.x / WIND_SAMPLES, y: w.y + s.y / WIND_SAMPLES };
  }

  const along = w.x * dir.x + w.y * dir.y;      // + tailwind, - headwind

  // Stability. A headwind raises the disc's airspeed, it flies more understable, and a RHBH
  // throw turns RIGHT (positive). A tailwind does the reverse and it fades left early.
  const turn = clamp(-WIND_TURN * along, -WIND_TURN_MAX, WIND_TURN_MAX);
  const a1 = a + turn;

  // Drift. The air carries the disc for as long as it is in the air, so the hang time the
  // throw was ALREADY going to have is the coupling - a floaty throw is at the wind's mercy
  // and a flat one is not. flightDur reads the pre-drift carry; using the result would be
  // circular.
  const k = flightDur(d) * WIND_DRIFT;
  const land = {
    x: lie.x + Math.cos(a1) * d + w.x * k,
    y: lie.y + Math.sin(a1) * d + w.y * k,
  };

  return {
    a: Math.atan2(land.y - lie.y, land.x - lie.x),
    d: Math.max(0.4, Math.hypot(land.x - lie.x, land.y - lie.y)),
  };
}
```

Two terms, and they are two different things, which is why crosswind needs no rule of its own:

- **The turn** is a rotation, so its cost in metres grows with carry. It reads only the
  *along* component, because that is the component that changes the disc's airspeed and
  therefore its stability. This is the effect the prompt describes for head- and tailwind.
- **The drift** is a translation by the full wind vector. Decomposed against the throw it does
  both jobs at once: the crosswind part pushes the disc sideways, and the along part lengthens
  a tailwind throw and shortens a headwind one. The prompt's crosswind rule — right-to-left
  pushes left, left-to-right pushes right — is nowhere written down as a rule. It falls out of
  adding a vector to a point, which is the strongest argument for this formulation.

The landing point is then converted back to an angle and a carry, so a pure crosswind changes
heading a lot and carry barely, while a pure tailwind changes carry a lot and heading not at
all. That also comes free from the vector add.

`Math.max(0.4, ...)` matches the clamp `release()` already applies. Only an absurd headwind on
a tap-in could reach it, and it exists so that the one path that could produce a zero-length
throw cannot.

### Tuning

```ts
// constants.ts
// ---------------------------------------------------------------- wind
export const WIND_DRIFT = 0.5;        // fraction of the wind's travel the disc picks up
export const WIND_TURN = rad(6);      // right-turn per tile/s of headwind
export const WIND_TURN_MAX = rad(25); // a blown-about disc still goes roughly forward
export const WIND_SAMPLES = 6;        // field samples along the nominal line
```

`WIND_DRIFT = 0.5` says a disc picks up half the air's displacement over its hang time. A disc
is not a balloon; it has its own momentum and it is only in the air for about a second.

What the numbers buy, on a 55 m throw (11 tiles, 1.18 s of hang time):

| wind | | drift | turn | lateral from the turn |
|---|---|---|---|---|
| 18 km/h (1 tile/s) | gentle breeze | 2.9 m | 6° | 5.8 m |
| 36 km/h (2 tiles/s) | fresh breeze | 5.9 m | 12° | 11.4 m |
| 54 km/h (3 tiles/s) | near gale | 8.8 m | 18° | 17.0 m |

Read against scatter: angular σ at that range is on the order of 10–14°, so a gentle breeze is
about half a sigma of bias and a fresh breeze is a full one. That is the balance the tuning is
aiming at — **wind should be worth aiming off for, and never bigger than the noise it hides
in.** A wind you can simply subtract is a tax, not a decision.

`WIND_TURN_MAX` caps the rotation at 25°, for the same reason `MAX_ERR_A` caps scatter at 40°:
past some point the throw stops being a throw you aimed. It engages above 4.2 tiles/s (75
km/h, a strong gale), which nothing on this hole authors — it is there for the storm hole, not
for this one.

### What falls out without being written

- **A blown throw is less affected by wind.** Overcharging costs 15–20% of the carry, which
  costs hang time, which is the drift coupling. The disc spends less time in the air for the
  wind to work on. Nobody writes that rule; it is `flightDur(d)` reading a smaller `d`.
- **A putt barely notices.** A 7.5 m throw hangs for 0.46 s, so a gentle breeze drifts it 1.2
  m and turns it 6°, which at that range is another 0.8 m. Wind is a driver's problem, which
  is correct.
- **A high throw suffers more than a flat one at the same carry.** Not yet — `flightArc` and
  `flightDur` are both functions of carry alone, so there is exactly one hang time per
  distance. When per-disc flight arcs arrive, this term is already keyed to the right
  quantity.

## The Indicator

Two indicators, with two different jobs. Conflating them is the mistake available here.

### Along the aim line — always drawn

**Not one arrow at the lie.** An arrow at the lie reports the wind where the player is
standing, and on this board that is not the wind that decides the throw. Measured against the
areas authored above, a full-power tee shot looks like this:

```
  0 m along the line   1.4 m/s   <- what an arrow at the lie would say
 11 m                  5.0
 22 m                  6.0
 33 m                  6.0
 44 m                  6.0
 55 m                  6.0
 ------------------------------
 path average          5.1 m/s   <- what actually deflects the throw
```

The tee sits in the outer band of the water area; the throw spends most of its flight in that
area's core. An arrow at the lie would be honest about the player's feet and wrong by 3.6×
about the shot, on the most important throw of the hole. That is exactly the failure this
indicator exists to prevent.

So **three arrows, spaced along the aim line** at 25%, 50% and 75% of the throw, each showing
the local wind where it sits. They lie **flat on the ground plane**, projected through
`proj()` like everything else, so they share the board's perspective rather than floating over
it as a HUD element.

Three arrows rather than one give the player the thing a single number cannot: they *fan* when
the throw crosses from one area into another, and they line up when it does not. Spatial
structure becomes something you read off the line you are about to throw down, which is the
only place it matters, and the area rings below stop being the only way to see the field.

**Each arrow's length on the ground is the distance the air travels in one second**, clamped
to `[0.6, 4]` tiles. That is not an arbitrary scale — the distance rings are already drawn at
2, 4, 6 and 8 tiles and labelled in metres, so the arrows are measured against a ruler that is
already on screen. An arrow reaching the first ring is 10 m/s of wind, and the player can read
that without being told.

The path-averaged speed, `"18 km/h"`, is drawn once in screen space at the last arrow's tip —
one number, and it is the number that goes into the deflection.

They follow the aim line, so they exist whenever it does: manual `idle`, `dir` and `power`.
With no line to sit on — mid-flight, or holed out — a single arrow falls back to the lie,
where it is the only honest thing left to report.

These arrows **fluctuate every frame** and are what the player watches while deciding, so by
the Snapshot contract they are canvas work: the 60fps wander must never go through `useState`.

They are drawn unconditionally, not behind a toggle. The aid toggles are there to test whether
the isometric view reads on its own, and terrain still reads with them off — you can see the
water. Wind cannot be seen. A game that deflects a throw with an invisible force is not
testing the view, it is cheating, and these arrows are the only reason wind is fair.

### The areas — behind a toggle

Per the prompt, each area also gets its own indicator at its epicentre, showing that area's
own speed and direction, plus **two rings: `core` and `radius`.** The inner ring is the edge
of the full-strength body, the outer one is the range at which the wind has reached exactly
zero, and the gap between them is the threshold band drawn to scale. One ring could only ever
show one of those, and which one it showed would be a lie about the other.

This is the structure of the field rather than the force on your disc, so it goes in `Toggles`
as `wind`, bound to `Digit5` beside the existing four, with a button in `Panel.tsx` alongside
the others. It is the layer that answers "why is it doing that" during tuning, and clutter
during play.

### The panel reading

One new field on `Snapshot`:

```ts
wind: {
  /** path-averaged resultant for the shot being aimed, right now */
  kmh: number;
  /** Beaufort band name */
  band: string;
  /** how it lies relative to the shot you are about to play */
  rel: 'calm' | 'head' | 'tail' | 'cross-LR' | 'cross-RL';
};
```

`kmh` is the **path average over the aimed line**, the same quantity `windDeflect` uses, for
the reason the arrows are spread along that line: the local reading at the lie is not what
moves the disc. One consequence to expect rather than to debug — the panel figure changes as
the player turns, because turning changes which air the throw will fly through. That is
information, not jitter.

`rel` is the field that earns its place. A compass bearing is not information a disc golfer
can act on — "258°" tells you nothing without the hole in front of you, whereas "headwind"
tells you to expect the disc to turn right. Both are computed against the angle currently
being aimed (`s.phase === 'power' ? s.lockedAngle : s.angle`), and `calm` is returned below a
threshold rather than letting a 1 km/h resultant be reported as a crosswind.

One nested field, not five flat ones, and it is all derived — the `WindField` itself never
crosses into the Snapshot. It is static for the round and 10Hz is the wrong rate to republish
a constant.

### The cone

`drawCone` must call `windDeflect` on every edge sample it builds.

This is not optional polish. The cone's contract is already written in `render.ts` — *"the
cone must show where the disc COMES TO REST, skid included — otherwise the aid is short by the
slide length and the throw reads as the game cheating you."* Wind is a larger discrepancy than
the skid, and it is a **biased** one, so a wind-blind cone would not merely be imprecise, it
would be centred on the wrong place. The cone shifts and shears with the wind, which is how
the player sees what to aim off by.

The cost is small against what `drawCone` already does: 44 edge samples × 6 field samples × 2
areas is around 500 extra `hypot` calls per frame, against 44 skid integrations of up to 600
steps each. The skid dominates by two orders of magnitude.

### The log

Wind joins `lastErr`, which is already the per-throw diagnostic and already carries `BLOWN
x1.7` in this shape:

```
-2.3° / +4.1m / skid 6.8m / wind +6°/-2.9m
```

Turn first, then the carry change, both signed. Suppressed entirely when the resultant is
calm, so a still round's log stays as short as it is today. `lastErr` has a defined lifetime —
the next release overwrites it — which is why the throw's wind goes there rather than into a
new field with a clearing rule nobody would remember.

## The Gust Is Frozen at Release

The wind field is sampled **spatially** along the flight path, but its **gust phase is frozen
at the moment of release**. `windDeflect` takes `t` and the caller passes the release time; it
is not re-evaluated during the flight.

Space and time are treated differently here on purpose:

- **Spatial variation is the feature.** A throw that crosses a pocket of strong wind has to
  feel it, or the areas are decoration. That is why the field is averaged along the line.
- **Temporal variation during the flight is noise.** A flight lasts 0.5–1.5 seconds against
  gust periods of 3.1 and 7.3 seconds, so integrating it would change the outcome by a few
  percent and would break the cone: the aid drawn at aim time would be computed from a
  different gust than the throw. An aid that is honest about the skid and dishonest about the
  wind is worse than no aid.

This makes the fluctuation a **decision** rather than decoration. The arrow is live, the cone
is live, and the wind that is blowing when you let go is the wind you get. Waiting for a lull
is a real play, which is the whole reason to render a wandering arrow rather than a steady
one.

It also has a problem, and it is an honest one — see open question 2.

## Testing

Per CLAUDE.md, new work in `src/game/` gets tests first, beside the code.

New — `src/game/wind.test.ts`:

- `falloff` is exactly 1 **everywhere in the core**, not merely at the epicentre — the
  property that separates this kernel from every single-radius one, and the reason `speed`
  means anything. It is 0 at exactly `radius`, 0 beyond it, and strictly decreasing across the
  band between.
- `falloff` is 0.5 at the midpoint of the taper band, which is the authoring promise the
  smoothstep symmetry makes and the one a well-meaning kernel swap would silently break.
- Its slope vanishes at **both** ends: sampled either side of `core` and either side of
  `radius`, the difference across the boundary is small. Neither rim is something a disc can
  cross abruptly.
- `core <= radius` for every authored area, and `falloff` still behaves when they are equal —
  a degenerate area is a hard-edged disc of wind, not a divide by zero.
- `windAt` over an empty field is exactly `{x: 0, y: 0}`, and over a field whose areas are all
  out of range likewise. Calm has to be exactly zero, not nearly zero, or every downstream
  term acquires a floor.
- Two opposing areas of equal strength cancel at their midpoint.
- **Two agreeing areas overlap to more than either peak.** Asserted so the absence of a clamp
  is a decision on the record rather than an oversight waiting to be tidied away.
- `gust` is deterministic in `t`, stays inside `±GUST_DIR` of the base heading and inside `1 ±
  GUST_SPD` of the base speed, and `wobble` sampled across 60 s never repeats within 0.5 s of
  itself — it is two incommensurate sines and the point is that it does not loop.
- `rollArea` lands inside `ROLL_DIR` and `ROLL_GAIN` for rolls at 0, 0.5 and 1, and calls no
  global RNG — the rolls are arguments.
- `kmh(1) === 18` and `beaufort` maps the band boundaries, including 0 to `calm` and 200 to
  `hurricane`.

New, in `src/game/physics.test.ts`:

- **Calm is identity.** `windDeflect` over an empty field returns `a` and `d` bit-for-bit
  unchanged. This is the regression that matters most: every throw in the existing suite still
  means what it meant, and wind is provably opt-in.
- **The sign tests**, which are the ones that earn their place — this is the failure mode this
  feature has, it is invisible until someone notices the disc fades the wrong way, and no
  amount of tuning finds it:
  - A pure headwind increases `a` (turns right) and decreases `d`.
  - A pure tailwind decreases `a` (fades left) and increases `d`.
  - A right-to-left crosswind moves the **landing point** to the left of the nominal line; a
    left-to-right crosswind moves it right. Asserted on the point rather than the angle,
    because the point is what the player sees and the angle is an implementation detail of
    getting there.
- The turn saturates at `WIND_TURN_MAX` under a wind strong enough to exceed it.
- The same wind deflects a long throw further than a short one, because the coupling is hang
  time.
- An area outside the throw's whole path contributes nothing — the path average has to
  actually sample the path.

Not covered, deliberately: the arrow, the rings and the `Digit5` binding, which live in
`render.ts` and `bindKeys`, where the project does not test.

`course.test.ts:33` asserts `tl(holeLength()) > MAX_D` — the pin is unreachable off the tee,
which is this hole's entire design premise. Wind now threatens it from a direction that test
cannot see: a strong tailwind adds carry. It keeps its current form, and the Monte Carlo in
the acceptance criteria is what actually checks it.

## How This Lands

Two commits.

1. **The field, visible and inert.** `wind.ts`, `WIND_AREAS`, the roll on `GameState`, the
   `Snapshot` field and the panel reading, the arrow, the area rings, the toggle and the key,
   and the whole test suite. Wind blows, the arrow moves, the panel reads it — and no throw is
   affected. Every test in the existing suite is untouched and still green, which is the
   strongest possible statement that the field is inert.
2. **The deflection.** `windDeflect`, the four coupling constants, the call in `release()`,
   the cone, and the `lastErr` line.

Split this way because commit 1 is the half most likely to be right and commit 2 is the half
most likely to need re-tuning or reverting. Reverting commit 2 leaves a game with weather in
it that does not yet blow the disc around — which is a coherent place to stand while the
tuning is argued about, and is exactly where the Monte Carlo might send it. Reverting one
commit that did both leaves nothing to stand on.

## Open Questions

1. **Wind may break this hole in either direction.** The hole is tuned so the pin is
   unreachable off the tee — 83 m against a 55 m arm — and so the water carry is roughly a
   coin flip at full power. A rolled tailwind lengthens every throw on the hole, the tee shot
   included. A rolled crosswind over the water makes the greedy line worse, possibly
   unplayable. The route dilemma is the thing under test on this board and wind is now the
   loudest voice in it. The Monte Carlo above is the gate and its numbers belong in this
   paragraph.

   **Decided in advance, so the number cannot be argued with when it arrives: if wind has made
   one route simply correct, `ROLL_GAIN` narrows first and `WIND_AREAS` moves second — the
   coupling constants do not.** `WIND_DRIFT` and `WIND_TURN` are calibrated against real disc
   behaviour and against the scatter curves; detuning them to protect one hand-authored board
   would be tuning physics to fit furniture, and the furniture is already scheduled for
   replacement by the measurement spec. Pre-committing matters because by the time the numbers
   exist the code will exist too, and every cut will feel expensive.

2. **Waiting out a gust is free, and that is probably wrong.** The gust is frozen at release,
   so the correct play in an unfavourable gust is to stand still for four seconds. There is no
   clock and no cost, so a patient player simply throws in the lull every time and the
   fluctuation becomes a tax on impatience rather than a decision. Three ways out, none chosen
   here:

   - A shot clock, which is a large and unrelated mechanic.
   - Make `GUST_SPD` small enough that waiting is not worth four seconds — which is close to
     admitting the fluctuation should not exist.
   - Freeze the gust at the **start of the charge** rather than at release, so the player
     commits to a gust before seeing how the power bar turns out. This is the cheapest and
     probably the right answer, and it is not specified here only because it wants play to
     confirm it.

   The honest position: shipped as specified, fluctuation is a timing game with a dominant
   strategy. It is worth shipping anyway because it costs nothing to change afterwards — the
   freeze point is one argument at one call site.

3. **Whether two areas read as two areas.** The prompt asks for 1–3 areas with distinct
   directions, but on a 100 × 70 m board with 30–40 m radii, the player may simply experience
   "the wind is different over there" as inconsistency rather than as structure. Nothing short
   of play answers this, and if the answer is no, the fix is one area on this hole and the
   field code is still right for the next one.

4. **Two numbers per area may be one too many to author.** `core` and `radius` are each
   legible alone, but every area now needs both chosen, and they interact with `speed`: a 40 m
   core at 6 m/s and a 20 m core at 9 m/s deliver similar totals down a line while feeling
   nothing alike. The alternative is to derive one from the other — a fixed band width, or
   `core = radius / 2` — which would cost the ability to author a tight gust and a broad
   steady breeze as different things. Kept as two numbers because that distinction is the
   reason to have areas at all, but if authoring the third area turns into fiddling, a fixed
   band width is the cut to make.

## Out of Scope

**Flight shape.** The disc flies a straight line, deflected once. A real disc in a headwind
turns right *and then* fades back left — an S-curve — and no straight line can express that.
This is the single largest simplification in the spec and the obvious successor to it:
`windDeflect` would return a path rather than a pair, and `Flight`, `basketEvent`, `drawDisc`,
`skidPath`'s start point and `drawCone` would all follow it. That is a larger change than this
entire spec and it is why it is not here.

**Throw technique.** Forehand, left-handed, hyzer and anhyzer. The prompt names the reason
these matter — an anhyzer into a headwind turns right violently — and every sign in this
document assumes right-hand backhand. Release angle is the natural next axis after flight
shape, because it multiplies the term this spec already has.

**Per-disc stability.** `WIND_TURN` is one global constant, which says every disc responds to
a headwind identically. It should eventually be per-disc: a stable driver resists the turn, an
understable one flips. The re-entry point is `WIND_TURN * d.turn` read where `DISCS` is read,
matching the pattern `specs/2026-09-19-disc-types.md` sets for `control` and `grip`. That spec
explicitly leaves stability out of its table, so neither spec blocks the other, and whichever
lands second adds one column.

If the disc types spec lands first, one interaction is already settled by both documents
agreeing: wind changes the carry *after* `effort` has been computed from the intended carry,
exactly as the flier does. Scatter is never computed from an outcome.

**Player skill.** `prompts/player skill level.md` will want wind to punish a weaker arm
harder, which it already does for free — hang time has a floor (`DUR_BASE`), so drift is a
larger fraction of a short throw than of a long one. Nothing here anticipates it further.

**Also out:** wind on the skid or on a disc already on the ground, wind varying with height,
elevation-driven wind (the plateau is authored as an area, not derived from terrain), wind
acting on a bounce-out, weather that changes mid-round, and any sound or particle treatment.
